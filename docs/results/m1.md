# M1 test results

Recorded 2026-10-06 on the author's machine (Intel Core i7-13700H, Windows 11, Go 1.25.6,
go.etcd.io/raft/v3 v3.6.0, Porcupine v1.3.1). CI re-runs everything with Go 1.26.

## Tests: 21 passed, 0 failed

Command: `make test` (`go test -count=1 ./...`). The suite was also run three times in a row
(`go test -count=3`); every run passed.

| Package | Tests | What it proves |
|---|---|---|
| `internal/kv` | 5 | Region ranges are half-open and the last one is unbounded; commands round-trip and malformed log entries are errors, not panics; empty keys, keys over 4 KiB, values over 64 KiB and non-client operations are refused; only refusals that prove nothing was applied are retryable |
| `internal/cluster` | 8 | One region is replicated on all three nodes; followers refuse proposals and name the leader; old epochs, unknown regions and invalid keys are refused; after a leader crash a new leader serves every acknowledged write and the restarted node catches up; a leader cut off from the majority cannot commit (its client gets "unknown outcome"), steps down, and its uncommitted write never appears; 60 keys with a limit of 8 split into contiguous regions that tile the key space, each with epoch at least 2 and identical on every replica; a restarted node rebuilds every region by replaying splits from its log; the directory never goes back to an older epoch |
| `internal/client` | 4 | Put, get and delete through whichever node leads; a client whose map predates 80 writes and several splits still reads every key, after being told its map was stale; requests survive a leader crash by following redirections; with every node down a request fails as "unavailable", meaning nothing was applied |
| `internal/lincheck` | 4 | The checker rejects a read that misses a completed write, accepts reads concurrent with a write either way, and treats a write with unknown outcome as possibly applied or not; 25 seeded histories from four concurrent clients under crashes, partitions, 2% message loss and splits are all linearizable |

Lint: `gofmt` clean and `go vet` clean. Audit: the five modules that are actually compiled
(`go list -test -deps`) have no known vulnerability on OSV.dev, and `govulncheck` finds none in
the code's call paths; the only reported ones are in the local Go 1.25.6 standard library (fixed in later
patch releases and not called by this code), and CI runs on Go 1.26.

## Do the checks catch real bugs?

Three deliberate bugs were put into the code one at a time; each made the suite fail, then was
removed:

| Bug | Caught by |
|---|---|
| The leader answers reads from its own memory instead of through the log | the linearizability test (a partitioned old leader serves stale values) |
| Writes are acknowledged when proposed instead of when committed | the leader-crash, isolated-leader and stale-map client tests |
| The epoch is checked when a request arrives but not when its entry is applied | the split test (writes land in a region that no longer owns the key) |

### What the numbers say

- **Splits follow the data.** Keys arrive in order, so every split cuts the last region at its
  median: fourteen regions of 125 keys and a last one of 250, each with its own Raft group and
  epoch (the last two share epoch 15 because a split gives both halves the new epoch).
- **Failover takes a few election timeouts.** With an election timeout of 10 to 20 ticks, every
  region the crashed node led had a new leader within about 60 steps; the client sees "not leader"
  and "node down" replies and retries, and every key stays readable through the majority.
- **Restart is a log replay.** The restarted node rebuilt all fifteen regions from its Raft logs,
  including the splits, and received the writes it missed within a few steps.
- **Linearizable under faults.** About 23,000 completed operations across 25 histories, with up
  to seven regions splitting while nodes crash and partition, all linearizable. The roughly 120
  writes with an unknown outcome are the ones whose leader crashed or was cut off before replying;
  the checker accepts either outcome for them, as a real client must.
- **Not yet measured:** throughput as nodes are added and thousands of seeds; both are M3.
